# ALEX v02 Phase 4.1.2 — medication DAILY BASIS reset rules (all 3 doses)

2026-09-15. Goal: `docs/ALEX_v02_redesign_spec.md` §4's DAILY BASIS reset
block for medication, mirroring Phase 3.2's spirometry design exactly, ×3
doses. 39 new rules total (13/dose): 3 simple resets
(`done_i`/`reminderStage_i`/`engaged_i` → 0) + a 4-gate day-slot boundary
cascade + a 1-gate min-clip, each of the 5 gates carrying a nested
assignment child — computing `$myMedication_windowEnd_i` the same way
`$spiroWindowEnd` was computed, reusing the shared
`$hyperparameterMorningEndHour`/`MiddayEndHour`/`EveningEndHour`
unchanged.

## Result

All 39 rules built and **verified byte-for-byte correct** (exact caption
string match against the intended design, not just structural spot-
checks) for doses 1, 2, and 3. Final rule-tree node count: 164 = 125
(before this phase) + 39 (new), an exact match — no stray or duplicate
rules anywhere in the tree.

## What was actually hard about this (in order)

### 1. `Duplicate` copies only the row, not its children

Confirmed live before building anything: selecting a gate WITH a nested
child and clicking `Duplicate` produces a same-depth sibling with **zero**
children — the child has to be created separately via `New` regardless of
how the parent was created. This shaped the whole build strategy: 8
top-level rows per dose via `Duplicate` (reliable), 5 nested children per
dose via `New` (unreliable, needs the established depth-verify-and-retry
discipline).

### 2. `_rules_nav.py`'s field-editing helpers had never been hardened

Editing the first duplicated dose-1 row crashed on the well-documented
"element is not enabled" Vaadin flakiness — but this time inside
`_open_field_popup`/`_fill_and_ok` (used by every `set_rule_comment`/
`set_rule_condition_x`/`_y`/`set_rule_result_variable` call), which had
*never* had retry protection, unlike `close_windows`/`open_rule_modal`
(hardened back in Phase 3.7). Fixed with the same `_click_retry` pattern
already used elsewhere in the file.

### 3. A stuck popup this time led to discovering a coaching edit-lock

Recovering from the resulting stuck "Enter name for variable:"-style popup
this time surfaced something new: after a browser restart (following the
established recovery playbook), re-entering the coaching hit **"Warning:
The coaching is currently locked by 'alex-dev-2'"** — the "Edit" button was
genuinely (not flakily) disabled. Root cause: killing the CDP browser
process while still inside the coaching's Edit view, without clicking
"Back to List" first, leaves PMCP's own per-coaching edit lock held
server-side (the editor's own onboarding banner warns about this — "it is
always a good decision to 'park outside'... leave the coaching using the
'Back to List' button" — apparently not just a courtesy). No force-unlock
control was found anywhere in the UI. The lock cleared on its own after
about 15-20 minutes (a session-expiry-adjacent wait, not confirmed exactly
how PMCP times it out).

This is very likely the actual explanation for this incident *and* the
2026-09-14 "session looks completely normal but every server round-trip
for loading more table rows silently stops completing" incident from the
day before — a materially better explanation than generic Vaadin
flakiness, given how severe and persistent both were (many real-click
retries over several minutes, unresolved by any amount of retrying).
Documented as a general platform-behavior finding in
`pmcp-portal-and-randomisation-groups.md` (persistent memory), since this
matters for every future live-portal session, not just this one.

### 4. The comparison/assign operator turned out to be a separate control

Building the first nested child (`New` on the evening-boundary gate) with
just `set_rule_comment`/`set_rule_condition_x`/`set_rule_result_variable`
(the pattern that worked perfectly for every top-level *edit*) produced a
rule that displayed as `--- calculated value equals ---` — content-wise
broken. Root cause, found by directly inspecting the modal's DOM: **the
comparison/assign operator (e.g. `"calculate value but result is always
true"`) is stored in a completely separate control from Rule[x]/Term[y]**
— a directly-clickable `.v-filterselect` (Vaadin ComboBox, the
click-to-open-a-list `-no-input` variant) sitting in the outer form, not
behind any of the 4 Edit-button popups. An *existing* rule (anything made
via `Duplicate`) already carries the correct operator forward from its
source and never needs this touched — which is exactly why every one of
Phase 3's rules and this phase's 24 top-level edits worked fine without
ever discovering this control. A *brand-new* rule (via `New`) starts on
PMCP's own default operator (confirmed live: `"calculated value equals"`)
and silently means the wrong thing until this is set explicitly.

Added `_rules_nav.py::set_rule_operator()` for this. While building it,
found it also needed its own reliability fix: a click on the operator
option can report success (no exception) while the actual selection
silently doesn't register — confirmed this happened on effectively every
one of the 10 nested-child creations across doses 2 and 3 (all 5 per dose,
both doses, on the very first attempt) once the higher-volume, faster
generalized build script was running. `set_rule_operator()` now always
re-reads the dropdown's own displayed text after selecting and retries
once if it doesn't match — this self-corrected every single occurrence
live, logged inline as `"nested correctly but a field failed (op=False...) -
re-editing in place"`.

### 5. Structural verification isn't enough — always verify content too

An earlier structural check (`parentUid`/`depth` match) reported dose 1's
evening-boundary child as correctly placed, and it was — but a *second*,
identical copy of the same child existed too (from an earlier recovery
step during the operator-discovery process, before the final generalized
script ran). Only found by the final byte-for-byte content verification
pass across all 39 rules, which is why that pass matters even when
structure alone already looks right. Deleted the duplicate; final state
confirmed clean (164 total nodes, exact expected count).
