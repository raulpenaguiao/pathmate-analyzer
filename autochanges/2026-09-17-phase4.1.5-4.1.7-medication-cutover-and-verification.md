2026-09-17. Goal: finish Phase 4.1 (medication reminders) by repointing
the new PERIODIC senders (4.1.3) at their new dialogs (4.1.4), retiring

## 4.1.5 — Decommission old bookkeeping

Repointed all 3 new PERIODIC senders' `Micro dialog to start` field from
the old 39-row dialogs to the corresponding new `(v02)` ones, via
`_rules_nav.set_rule_micro_dialog()` (already proven in 4.1.3), each
independently re-verified by reopening the rule and reading the
filterselect fresh afterward (the helper's own internal check reported
`False` for all 3 — the same innerText-unreliable pattern already
documented for this control — but every fresh re-open confirmed the
value had actually landed).

Then deleted 8 obsolete rules from the live Rules tree, found by a broad
caption search for anything medication-related predating this
redesign, confirmed against each other's parent/child context before
deleting anything:

- **3 old "ask if still want reminded" reschedule chains**
  (`Check whether $my{First,Second,Third}Medication_userRequestedNewTime=1`,
  each with 2 children: a flag-reset and a "Rescheduled reminder to
  inhale Nth medication dose" leaf — 9 nodes total via 3 cascading
  deletes). This mechanism is exactly what spec 3.2 already replaced for
  spirometry in phase 3.5 ("the existing USER INTENTION mechanism...
  updates the time variable directly" instead of a dedicated
  reschedule-and-refire branch) — not spelled out by name in this task's
  original TASKS.md text, found while confirming the sender/variable
  cleanup below and removed to match the same principle.
- **2 old pre-4.1.3 PERIODIC senders** ("Send regular reminder for
  first/third of the day controller medication inhalation"). Deleting
  the "third dose" one cascaded away dose 2's sender too, since it was
  the already-known mis-nested child (the 2a/2b bug from
  `docs/pileup_findings_ALEX_v01.md` Finding 2) — one delete both
  retired the old firing mechanism and resolved the mis-nesting, since
  dose 2's old sender had no function beyond firing its own
  now-superseded reminder.
- **3 old bookkeeping-variable resets** — 2 duplicate
  `Reset $medicationNumberOfRegularRemindersIssued to 0` rules (a
  pre-existing v01 duplicate-rule bug, unrelated to this redesign,
  cleaned up as a side effect of retiring the variable) + 1
  `Reset $myMedication_NumberOfInhalationsOfTheDayCompleted to 0`.

This bulk-delete needed the user's explicit go-ahead — the auto-mode
classifier blocked the script even after the user said "yes" in chat,
requiring an actual `/permissions` grant before it would run. Confirmed
via a genuine fresh re-navigation afterward: zero remaining references
anywhere to any of the 6 retired identifiers, all 3 new senders still
present and correctly pointed at their `(v02)` dialogs.

## 4.1.7 — Export verification

Took 3 attempts. Runs 1-2 failed before the sweep even started — a
leftover "Edit rule:" modal (from the 4.1.5 repointing work, showing all
fields "(no value set)" since a sender rule's own condition fields are
deliberately always empty by design) was blocking the entire page behind
a modality curtain; every click anywhere silently failed to register
until it was found and closed via `close_windows()`. Run 3 succeeded:
`data/exports/coaching_alex-v01-zum-ausprobieren_phase4.1-verify.json`,
6m 31s.

Rules and Variables sections (the ones with real content for this phase)
both swept cleanly:
- 171 rule-tree nodes — exact match to 4.1.6's own live count.
- All 3 new senders present with the right captions.
- **Zero** remaining references anywhere to any of the 6 identifiers
  retired in 4.1.5.
- All 16 variables added this whole phase present (13 from 4.1.1 + 3
  `$myMedication_confirmAnswer_i` from 4.1.4).

**The Micro Dialogs sweep hit a pre-existing, unrelated tool bug**: past
roughly the 20th of 90 menu targets, `_menu_nav.py::open_folder_path`
started raising `RuntimeError("top '...' not found")` for almost
everything remaining — including all 3 new medication `(v02)` dialogs
and the 3 original 39-row ones — driving the coherence check's ~70%
node-count "drift" flag. Not a regression from this session's work, just
this run's share of the tool's own known scrape gaps (3.7 hit the same
category, described there as "the known per-run popup-hover scrape
gaps"). Root cause not fully chased down — plausibly the widened
12000px window (set once at sweep start via `_widen_for_menubar` so the
menubar doesn't collapse into a `►` overflow) getting reset partway
through by some later navigation, silently reintroducing the collapse
for later targets. Worth a dedicated look before 4.2+ leans on this
export for dialog-content verification, since a folder deep in
alphabetical/tree order failing silently-ish (as a caught, logged
exception, not a crash) is an easy thing to miss in a wall of otherwise
normal output. Not a blocker here: this phase's actual dialog content
was already independently verified byte-for-byte via live DOM checks
(genuine fresh re-navigations, not just in-session reads — see the
4.1.4 log for why that distinction matters on this tab) during 4.1.4 and
4.1.6, and this export's clean Rules/Variables data corroborates that
rather than needing to duplicate it.
