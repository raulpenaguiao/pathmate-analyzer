## Documentation research before building (per explicit user instruction)

Before writing anything, read PMCP's own documentation
(`my.pathmate.app/pmcp-documentation/doc-5-0/sections/coachings/rules` and
`.../variables`) rather than continuing to infer rule-engine semantics from
precedent alone. Confirmed several things that had only been inferred
before:

- **Nesting = AND, siblings = OR** — explicitly documented: *"If the parent
  condition is preselected, the new condition is automatically created as a
  child condition, linking the rules with an AND-condition. If two rules are
  at the same hierarchy level, they are linked with an OR-condition."* This
  is the first *documented* (not just precedent-inferred) confirmation of
  the mechanism the day-slot rule and 3.2 both already relied on.
- **Division is a documented, real operator**: Example 4 in the docs is
  `($score1+$score2+$score3)/3 create value but result is always true` —
  directly validates 3.2's `$spiroMesTime+$hyperparameterSpiroGraceMinutes/60`
  expression, which had been flagged as *unverified* pending exactly this
  kind of check (see the new `pmcp-rule-expression-verification` memory).
- **`$participantOpenQuestions`** (system variable, "Open questions for the
  participant") and **`$participantOpenDialogCascades`** exist and are
  documented in the Variables reference. `$participantOpenQuestions` is used
  directly below as the "no dialog open" guard the spec's 2.1a priority
  model needs — the closest real primitive to "effective tier ≥ P1", see
  the Limitations section.
- **The "dialog cascade" terminology is a real, documented PMCP concept**,
  independent of anything this project guessed: *"Cascade: In this case, you
  jump to the other micro dialogue and then return to the point from which
  you left when the other dialogue has ended."* — a cascade is PMCP's own
  return-stack mechanism for dialog-to-dialog transitions. This corroborates
  Phase 3.1's finding about the "clears the current dialog cascade" message
  checkbox: clearing the cascade means not pushing a return-entry onto that
  stack, i.e. exactly the delete-not-reactivate behavior the spec wants.
- **DAILY BASIS rules evaluate once at 00:00 and freeze**; PERIODIC BASIS
  re-evaluates continuously. Documented explicitly, matches how 3.2 (reset,
  DAILY) and 3.3 (firing, PERIODIC) were already split.
- Confirmed **every sender rule in this coaching has an empty own condition**
  (`ruleExpr: null` in all 25 of Stage 3's captured sending rules, and in the
  live existing spirometry firing rule inspected below) — sender rules rely
  entirely on their ancestor gate chain; they are never simultaneously a
  comparison AND an action in one row. Followed this convention exactly
  rather than trying to combine a real condition with an action in a single
  rule.

## Grounding in the existing v01 firing rule

Before designing, read the **existing** (soon-to-be-superseded, not touched)
spirometry PERIODIC firing rule live:
```json
{
  "actions": ["start_micro_dialog"],
  "microDialogToStart": "Prompt patient to conduct daily spirometry",
  "sendHourVariable": "$spiroMesTime",
  "notAnsweredTimeoutMinutes": 240,
  "ruleExpr": null
}
```
This confirmed the exact field pattern to replicate: `Hour to send message`
set to `$spiroMesTime` (not "0 = immediate"), 4h default timeout untouched
(Phase 1's platform limitation — still no way to set otherwise), and no
condition on the sender's own row.

## What was built

A 5-level AND-gate chain under `Execution on PERIODIC BASIS` → `🚀 Only
perform if daily rules have been already performed` (same parent as 3.2's
new rules), implementing spec §3.2's first IF-block:

```
Gate 1: $spiroMesDone calculated value equals 0
  Gate 2: $timeDecimal calculated value is bigger or equal than $spiroMesTime
    Gate 3: $timeDecimal calculated value is smaller than $spiroWindowEnd
      Gate 4: $spiroReminderStage calculated value equals 0
        Gate 5: $participantOpenQuestions calculated value equals 0
          → Fire spirometry reminder: Start micro dialog = "Prompt patient
            to conduct daily spirometry", Hour to send message = $spiroMesTime
            (condition-free sender, matches the 100%-consistent pattern above)
          → $spiroReminderStage = 1  (sibling child, also condition-free)
```

7 new rules total. Both children of Gate 5 fire together once every ancestor
condition holds — the sender starts the reminder dialog, and the sibling
marks it as sent so the next periodic tick's Gate 4 check blocks re-firing
for the rest of the window (spec's "at most one instance... at a time" rule,
2.2b.6).

## Limitation: `$participantOpenQuestions==0` approximates, doesn't fully implement, spec 2.1a

Spec 2.1a's actual guard is "no dialog open with *effective* tier ≥ P1" —
i.e. an idle low-priority P2 reminder should **not** block this from firing,
only a real P1 or an *engaged* P2 should. `$participantOpenQuestions` is a
flat count with no tier awareness — it can't distinguish "an idle low-
priority thing is open" from "something important is open". Using
`==0` is **stricter than spec** (never fires over anything open at all, even
something spec would have let it interrupt) but **safe** (never fires over
something more important) and, critically, is built entirely from a real,
documented system variable rather than an invented one. Flagging this as a
known simplification for future refinement (would need per-dialog-tier
tracking that doesn't exist as a single system variable today) rather than
a bug — the proof-of-concept prioritizes never causing new pile-up over
exactly replicating the priority nuance.

## Deferred to 3.4, not missing from 3.3

Spec §3.2's **second** IF-block (window-expiry: "let the time-out question
close itself... no manual message needed") is not a separate rule at all in
this design — its own text defers to "the expiry message configured on the
question itself" (§3.3). Phase 1/3.1 already found that field only offers
fixed presets (1/5/10/30/60/infinite minutes), not a dynamic value tied to
`$spiroWindowEnd` — so how this actually gets configured is a **dialog-
message decision for Phase 3.4**, not something 3.3's rule tree needs to
(or usefully could) implement. No rule was added for it here; this is a
deliberate scope boundary, not an oversight.

## Interruption: Vaadin session expiry

Mid-session (during the documentation research, on a separate tab), the
main PMCP tab's Vaadin session expired — a `.v-Notification` reading
"Session expired! ... click here to continue" appeared, and clicking it
landed on the login page (not a resumable state). **No rule-writing work was
lost** — everything committed before the expiry was already persisted
server-side, confirmed by re-expanding the tree after the user
re-authenticated and finding all of 3.1/3.2's rules intact with zero
regressions. The trigger looks like plain session-timeout from an extended
gap between actions on the main tab (the docs research happened on a
separate `ctx.new_page()` tab), not something the write tooling caused.
**Lesson**: if a rules-tab session goes idle for an extended stretch (e.g. a
long documentation-reading detour), check for a `.v-Notification` with
"Session expired" text before assuming a stalled click is the usual
"element not enabled" Vaadin flakiness — they produce different symptoms
(a normal stale-selection retry still finds the toolbar buttons enabled; an
expired session's Edit click opens no window at all, silently, with the
button still showing `enabled` state throughout).
