# 2026-09-11 — ALEX v02 redesign, Phase 3.1: cascade-clear checkbox tested

**Coaching:** "ALEX v01 zum Ausprobieren" (sandbox — not production, per the
user).
**Driving:** Claude, over the user's CDP session.
**Goal:** `TASKS.md` Phase 3.1 — confirm the "clears dialog cascade"
checkbox (flagged untested in the Phase 0 recon) is genuinely writable and
persists, before Phase 3.4's dialog rebuild relies on it as the
delete-not-reactivate lever the whole spec assumes.

## Mechanical test: PASSED

Target: `👋 Hello` (onboarding dialog, no reminder/interruption logic — safe,
low-risk), row 1 (`Nice to see you $participantName!`, a plain message).
Round-trip test:

1. Opened the message editor, expanded "Show additional settings", read
   baseline: `This message clears the current dialog cascade (and
   remembered questions)` = unchecked, **not disabled**.
2. Clicked it on. Diffed every checkbox in the form before/after — **no
   sibling checkbox reacted** (not mutually exclusive with "deactivates and
   remembers", the two "recalls former deactivated questions" variants, or
   anything else in the block — it's an independent toggle).
3. Saved (`Close` — confirmed once again to be a real commit on this editor,
   same as the Rules-tab editor and every other PMCP modal found so far, not
   a plain cancel).
4. Reopened the same message fresh: checkbox read back as **checked = True**
   — the write persisted server-side, not just client-side state.
5. Toggled it back off, saved, reopened again: back to **checked = False**,
   matching the original — no residual change left on this message.

## Correction to the Phase 0 recon's assumed mechanism

Phase 0 (and the first `probe_cascade_checkbox.py` pass, written against a
dev/test dialog that Phase 2 has since deleted) assumed this checkbox lives
behind a **nested sub-editor**, reached via one specific "Edit" button in the
outer "Edit micro dialog message:" form. That's wrong, at least for a plain
message row like this one: **all the behavior checkboxes — including the two
cascade-clear variants, the "clears ALL dialog cascades" variant, the
"will not be cleared on clear all" variant, "deactivates and remembers", both
"recalls former deactivated questions" variants, "is sticky", the two push-
notification variants — sit directly in the outer form**, immediately below
the "Show additional settings" toggle, immediately live and clickable (no
sub-window, no extra Edit click). Full sequence observed in outer-form DOM
order:

```
[ ] This message's answer can be cancelled ...        (disabled on this row)
[ ] This message deactivates and remembers all former open questions
[ ] This message blocks the micro dialog until answered/unanswered   (disabled on this row)
[ ] This message recalls former deactivated questions from last deactivation
[ ] This message is sticky in the client
[ ] This message recalls former deactivated questions from most recent still filled deactivation
[ ] This message is ONLY a push notification and NOT appears in the chat
[ ] This message clears the current dialog cascade (and remembered questions)   <- tested
[ ] This message is ALWAYS announced by a push notification
[ ] This message clears all dialog cascades (and remembered questions)
[ ] The cascade (and rem. quest.) of this message will not be cleared on clear all
Minutes after sending until message is handled as unanswered: [1] [5] [10] [30] [60] [infinite]
```

Two checkboxes (`answer can be cancelled`, `blocks the micro dialog`) *are*
disabled on this particular row — likely gated on `This message expects to
be answered by the participant` being unchecked (this row is a plain
one-way message, not a decision point). **Not yet re-confirmed on a row that
does expect an answer** — Phase 3.4's actual spirometry messages will be
decision points, so re-check this disabled-state gating there, don't assume
today's finding transfers unchanged.

## What this does and doesn't establish

**Established**: the field is real, live, independent of its siblings, and
round-trips correctly through a save/reload cycle. Phase 3.4 can rely on
this checkbox being settable exactly the way the spec's design assumes.

**Not established, and out of scope for what's practically testable via the
editor alone**: the actual *runtime* effect (does checking it really cause
"delete, don't reactivate" the next time a higher-tier dialog interrupts).
Confirming that would need a live participant walking through an actual
interruption scenario — no such test harness exists yet (Stage-4 chat
simulator, a separate workstream, isn't built). Checked the built-in PMCP
Documentation panel (`my.pathmate.app/pmcp-documentation/doc-5-0`) for
corroborating language — searched the Micro Dialogs, Message Configuration
Table, Timing Messages, and Coaching Dialogues pages for "cascade",
"reactivat", "deactivat", "unanswer", "priorit" — **none of those terms
appear on any of the pages checked**. Either the terminology lives on a page
not reached from the top-level nav in three hops, or under a different
version than v5.0, or was originally sourced from documentation text that
has since changed. Not pursued further — diminishing returns for a docs
side-quest when the field's own wording ("clears the current dialog
cascade") already matches the spec's design intent directly, and the
mechanical round-trip is what this task actually needed to confirm.

## Session hygiene notes

- Every `Close` on this message editor (even with zero field changes) posts
  a real "The micro dialog message has been updated" toast and leaves a
  `.v-Notification` element that **intercepts pointer events** on the next
  script's first click — any future tool touching this editor repeatedly in
  one session should dismiss it (`page.locator(".v-Notification").first.click()`)
  before its next action, not just wait it out.
- The Documentation nav item (top-level left-nav "Documentation", not the
  Variables-tab sub-button bug from Phase 3's variable-creation session) opens
  a `.v-window` containing a cross-origin iframe
  (`my.pathmate.app/pmcp-documentation/...`) that Playwright's `page.frames`
  does not enumerate reliably — reading its content needs a **separate tab**
  navigated to the iframe's `src` directly, not `frame_locator`/`content_frame()`
  on the original page.
