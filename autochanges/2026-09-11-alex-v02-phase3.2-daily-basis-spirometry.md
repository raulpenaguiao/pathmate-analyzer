`$spiroMesDone`'s existing reset rule needed **no change** — confirmed

## Design: min() without a min() operator

A single PMCP rule row can't both compare two values AND store an unrelated
third value — the store target always receives either the comparison's
boolean result or the calculated Rule[x] expression itself (operator-
dependent), never an independently-chosen literal. So `min(A, B)` needs two
rules: an unconditional base assignment, then a comparison **gate** whose
nested **child** does the conditional overwrite (exactly the pattern
confirmed for `$currentDaySlot` in the previous session, and precedented
live in the coaching itself — e.g. `Check whether
$userRequestedNewTimeForEducationalContents=1` gating a nested reset).

`end-of-slot-after($spiroMesTime)` (the slot **containing** `$spiroMesTime`,
not wherever `$spiroMesTime + grace` happens to land — those differ exactly
when grace pushes the window into a later slot, which is the spillover case
the spec is designed to prevent) needed its own 4-gate cascade, structurally
identical to the `$currentDaySlot` rule but keyed on `$spiroMesTime` instead
of `$systemHourOfDay`, and storing the **boundary hour** (a number) instead
of a slot name:

```
Gate: $spiroMesTime < $hyperparameterEveningEndHour   → $spiroWindowEnd = $hyperparameterEveningEndHour   [widest, runs first]
Gate: $spiroMesTime < $hyperparameterMiddayEndHour     → $spiroWindowEnd = $hyperparameterMiddayEndHour
Gate: $spiroMesTime < $hyperparameterMorningEndHour    → $spiroWindowEnd = $hyperparameterMorningEndHour  [narrowest, runs last, wins]
Gate: $spiroMesTime >= $hyperparameterEveningEndHour   → $spiroWindowEnd = 24                              [night — no "next day" hyperparameter exists, 24 (midnight) used as the boundary]
```

Then the actual min-clip, in one more gate+child pair:
```
Gate: ($spiroMesTime + $hyperparameterSpiroGraceMinutes/60) < $spiroWindowEnd(= boundary, from above)
  → $spiroWindowEnd = $spiroMesTime + $hyperparameterSpiroGraceMinutes/60
```
(if base is *not* smaller than the boundary, `$spiroWindowEnd` correctly
keeps the boundary value already set by the cascade above — no `else`
needed).

**Grace-minutes-to-hours conversion**: time variables in this coaching are
decimal hours (precedent: `r-053`, `$userSetBedtime-0.17` for "10 minutes
before bedtime" via plain subtraction), so `$hyperparameterSpiroGraceMinutes`
(stored in minutes, per spec) needed `/60` inline in the expression:
`$spiroMesTime+$hyperparameterSpiroGraceMinutes/60`. **Confirmed this
expression syntax is accepted and persists exactly as typed** (division
inside a Rule[x] box, not previously used anywhere in this coaching) — read
back unchanged after save. Not independently confirmed to *evaluate*
correctly (no live participant run available), but every other arithmetic
expression in this coaching uses the same plain-infix style, so there's no
reason to expect `/` is treated differently from `+`/`-`.

Total: 12 new rules (2 simple resets + 4 gate/child pairs for the boundary
cascade + 1 gate/child pair for the min-clip).

## New/reconfirmed mechanics

- **`Duplicate` appends to the END of the parent's full children list, not
  immediately after the source row** — a correction to what the previous
  session's day-slot-rule log implied. That session's source rows always
  happened to already be the last child, making "after source" and "at the
  end" look identical. Here, duplicating from a rule in the *middle* of a
  ~30-rule reset list landed the copy at the very end of that list, confirmed
  by tree position, not next to the source. Both `Duplicate` and `New`
  apparently share this same "append to target parent's children" insertion
  logic.
- **The `New`-button top-level-misplacement bug (logged last session) is
  still very much present and just as frequent**: of the 5 child-nesting
  steps this rule needed (4 boundary gates + 1 min-clip gate), **4 landed as
  a stray top-level section on the first attempt** and needed delete-and-
  retry; only 1 succeeded first try. No pattern found that predicts which —
  same coin-flip behavior as before. The verify-by-depth-after-commit
  discipline caught every one before it could pollute the coaching.
- Also reconfirmed: the "element is not enabled" Edit-button quirk, and a
  `close_windows()` timeout that turned out to mean the modal had *already*
  closed from a slightly-delayed prior click (not a real failure) — both
  already-documented flaky patterns, resolved by re-checking state and
  retrying, no new fix needed.
