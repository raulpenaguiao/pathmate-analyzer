## New mechanics found while building message 1 (the initial push notification)

1. **Bilingual message text is NOT a single combined string** — the "Edit
   text (with placeholders):" popup has two tab buttons, "English (GB)" and
   "Romanian (RO)", sharing one textarea that swaps content per selected
   tab. **Mistake made and caught**: first attempt filled the textarea with
   the literal combined `"en-GB: ... / ro-RO: ..."` display-format string
   (copied from how dumps *render* existing messages) — this is only a
   read-only rendering convention, not the real input format, and produced
   a broken `"en-GB: en-GB: ..."` double-prefixed English field. Fixed by
   clicking each tab explicitly and typing the plain per-language text into
   each. **Any future message-authoring tool must click the language tab
   before filling the textarea, every time** — `_rules_nav._fill_and_ok` is
   safe for Rules-tab popups (single value, no language tabs) but is wrong
   for this specific message-text popup.
2. **The cascade/deactivate/recall checkbox block requires the message to
   already be saved once** — on a brand-new, never-saved message, all of
   `deactivates and remembers`, both `recalls former deactivated
   questions...` variants, `clears the current dialog cascade`, `clears all
   dialog cascades`, and `will not be cleared on clear all` are disabled;
   the *first* save's Close/OK persists the base message, and *reopening*
   it via Edit is what unlocks these checkboxes. (Only `answer can be
   cancelled` and `blocks the micro dialog` stay disabled beyond that,
   gated on "expects to be answered" as found in Phase 3.1.)
3. **"This message is ONLY a push notification and NOT appears in the
   chat" is mutually exclusive with the whole cascade/deactivate/recall
   block** — checking it disables all of those checkboxes; unchecking it
   re-enables them. This is a real tension with spec §3.3 step 1's design,
   which wants the reminder to be *both* a push notification *and*
   cascade-clearing. **Resolved by using "This message is ALWAYS announced
   by a push notification" instead** — functionally still delivers a push
   notification, but does not disable the cascade checkboxes (confirmed:
   checked both together, saved, reopened, both persisted correctly).
   `ONLY a push notification` presumably means "never rendered in the
   in-chat cascade at all," which is why cascade-*clearing* is meaningless
   for it — `ALWAYS announced by...` instead means "push notification
   *in addition to* the normal in-chat presentation," which does
   participate in the cascade normally.

**Known limitation to carry forward**: the message-level "Minutes after
sending until message is handled as unanswered" field only offers fixed
presets (1/5/10/30/60/infinite minutes per Phase 0/3.1), not a value tied to
the dynamic `$spiroWindowEnd`. Planned resolution: use the `60`-minute
preset as the closest available finite option (an `infinite` timeout would
leave `$participantOpenQuestions` permanently non-zero if never answered,
which would then wrongly block every *other* P2 reminder's Phase 3.3 firing
gate forever — a correctness reason to prefer a finite preset over
`infinite`, not just an approximation-quality one). This under-approximates
the spec's ~180-minute grace window; flagged here for whoever revisits
timing precision later, not silently decided.
