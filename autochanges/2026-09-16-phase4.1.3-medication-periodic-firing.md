# ALEX v02 Phase 4.1.3 — medication PERIODIC BASIS firing rules (all 3 doses)

2026-09-15/16 (spanned two sessions). Goal: `docs/ALEX_v02_redesign_spec.md`
§4's PERIODIC BASIS firing block for medication, mirroring Phase 3.3's
spirometry design **plus the `participantOpenQuestions==0` guard** that
2a/2b found missing from every non-spirometry reminder
(`docs/pileup_findings_ALEX_v01.md`) — this is the actual pile-up fix for
medication. Per dose: `done_i==0` AND `timeDecimal>=doseTime_i` AND
`timeDecimal<windowEnd_i` AND `reminderStage_i==0` AND
`participantOpenQuestions==0` → fire (start the dose's existing micro
dialog, 240min not-answered timeout), set `reminderStage_i=1`. 7 rules per
dose (5 gates + sender + leaf) × 3 doses = 21 new rules.

## Result

All 21 rules built and **verified byte-for-byte correct** (exact gate
captions, sender `actions`/`microDialogPath`/`sendHourVariable`/
`notAnsweredTimeoutMinutes`, leaf caption — not just structural
spot-checks) for doses 1, 2, and 3, with zero stray/duplicate rules
remaining anywhere in the chain.

## What was actually hard about this (in order)

### 1. `New` opens a "Create rule:" modal — a previously-undocumented mechanic

Unlike editing an existing row, clicking `New` on a tree node doesn't
insert a row directly — it opens a "Create rule:" modal (same field
layout as "Edit rule:"). Clicking "Close" on it commits the rule; there is
no separate Cancel. This matters because every nested gate in this chain
(everything past Gate 1) has to be built this way — `Duplicate` can only
produce a same-depth sibling under an *existing* parent, never new
nesting (confirmed directly in 4.1.2).

### 2. `set_rule_hour_variable()` was fundamentally broken, and the dialog
picker needed pagination too

The sender step needs two more filterselect-driven fields beyond the
operator (already handled since 4.1.2): "Micro dialog to start" and "Hour
to send message". Both turned out to be the same `-no-input`,
click-to-open-a-list Vaadin ComboBox family as the operator control, at
filterselect index 2 and 3 respectively in the outer form (0 = operator,
1 = message group). `set_rule_hour_variable()` as it existed before this
phase always returned `False` — it was matching the wrong DOM target
entirely (an outdated click-inner-`<input>` + `.gwt-MenuItem` approach
that never matched the actual widget markup). Rewrote it to match the
proven filterselect pattern. Both this and the micro-dialog picker are
also **server-paginated** (10 options/page via `.v-filterselect-nextpage`)
since one lists all ~334 coaching variables alphabetically and the other
lists every dialog/folder as a full `"A > B"` path string — added
pagination loops to both (`set_rule_micro_dialog()` new, capped at 20
pages; `set_rule_hour_variable()` rewritten, capped at 40 pages since
`$userSetDesired...` sorts near the end of the alphabet).

### 3. Severe "clicks don't register anywhere" incident #1 — resolved only
by the user manually opening a new browser window

Mid-build (after Gates 2-4 of dose 1), every click stopped registering as
a real selection/action anywhere in the app (Rules tree, Coachings-list
row, toolbar Edit button — confirmed via `aria-selected`/`v-selected`
never becoming true, and the Edit button genuinely `v-disabled`). Two
consecutive full clean restarts (kill Chrome, relaunch via
`start_pmcp.sh`, fresh login) did **not** fix it — unprecedented at the
time, since every earlier incident this project had resolved with a
restart. Stopped and asked the user to check the physical browser rather
than keep guessing; the user reported it had logged out and that they had
personally started an entirely new browser window — after which clicks
worked immediately. The connection later dropped again mid-edit
(`TargetClosedError`) when the user had to close their computer, which
also left a stuck "Create rule:" + "Edit comment:" modal pair open;
pressing Escape eventually closed it (cancelling that incomplete rule,
the safest outcome since it was mid-edit anyway) but triggered a further
logout.

### 4. Severe incident #2 on session resume, this time root-caused

Resuming the build hit the *same* symptom again — but this time even a
freshly killed-and-relaunched browser with a brand-new login couldn't
select a table row or click sidebar nav. Investigation found the real
cause: `start_pmcp.sh`, when it finds an already-listening CDP browser,
**reuses it and opens/attaches to another logged-in tab** instead of
replacing the existing one. Repeated restart attempts during
troubleshooting had left **two logged-in PMCP tabs in the same browser**,
which appear to fight over the server's single-session-per-account state
— producing the exact "no click registers" symptom plus spurious logouts
and coaching-lock churn, independent of whether the Chrome process itself
was freshly started. Fix: check `len(browser.contexts[0].pages)` and close
every extra tab before doing anything else — this alone resolved it
without needing the user to touch anything. Documented as a general
platform finding in `pmcp-portal-and-randomisation-groups.md` (persistent
memory) since it likely explains some of incident #1 too, not just #2.

### 5. Coaching edit-lock recurred repeatedly, with inconsistent clear times

Every forced browser kill during the above two incidents (unavoidable —
the browser was unresponsive) re-triggered the coaching edit-lock
documented in 4.1.2, under the automation account itself (`alex-dev-2`
from `.env`, not a mystery third party). Clear time was inconsistent this
session — as fast as ~2 minutes on one occurrence, closer to the
previously-documented ~15-20 minutes on another. No force-unlock control
exists; used a polling loop (recheck the Coachings-list banner text every
45-60s) rather than guessing a wait time. Memory updated to stop implying
a specific fast clear time.

### 6. One stray rule from the stuck-modal recovery, and a collapsed tree
on the fresh page

The stuck "Edit comment:" popup from incident #1 (see #3) left behind one
blank-comment duplicate of dose 3's Gate 2 (correct field values, no
comment — so it didn't match the cleanup helper's comment-substring
search and survived as a silent extra sibling). Found only by the final
byte-for-byte verification pass, same lesson as 4.1.2: always re-verify
final state fresh. Separately, a brand-new page load starts the Rules
tree collapsed (previous scripts had relied on whatever expand state a
long-lived session left behind) — every build script now calls
`expand_all()` right after `ensure_rules_tree()` explicitly.

## Tooling changes (committed, reusable for 4.1.4+ and every later Phase-4 area)

- `_rules_nav.py::_mouse_click()` — real OS-level `page.mouse.click()` at
  an element's actual bounding-box coordinates, wired as a fallback into
  `_click_retry`, `close_windows`, `open_rule_modal`, `select_node`,
  `ensure_rules_tree`. For a `Locator.click()` that hangs indefinitely
  with no modal/overlay/notification to explain it — distinct from the
  well-documented "element is not enabled" flakiness, and explicitly not
  the same as a dangerous JS-dispatched `element.click()` (confirmed
  elsewhere to be able to desync the Vaadin session) since this drives a
  genuine input event, just skipping Playwright's own extra
  stability pre-check.
- `_rules_nav.py::set_rule_operator()` (added in 4.1.2, reused
  unchanged), `set_rule_micro_dialog()` (new), `set_rule_hour_variable()`
  (rewritten from broken to working) — all with pagination where the
  underlying list is server-paginated.
- `pmcp-portal-and-randomisation-groups.md` (memory) — new section on the
  duplicate-tab root cause and how to check/fix it fast, plus a
  correction that the edit-lock clear time is inconsistent rather than
  reliably fast.
