## General Micro Dialogs platform mechanics found this session

These are not spirometry-specific — they apply to building or editing any
micro dialog message or decision point in this coaching, and should inform
any future dialog-authoring work (Phase 4 will need all of them):

### Message editor

- **Bilingual text fields use a tab switcher, not a combined string.** Any
  "Edit text (with placeholders):"-style popup (message text, answer
  options) has "English (GB)" / "Romanian (RO)" tab buttons sharing one
  textarea. Click the tab, type, switch tab, type again, then OK. Never
  type the read-only display convention (`"en-GB: ... / ro-RO: ..."`)
  directly into the field — that produces a broken double-prefixed value.
- **The cascade/deactivate/recall checkbox block requires the message to
  already be saved once.** All disabled on a brand-new unsaved message;
  save it, reopen via Edit, and they unlock (except the two gated on
  "expects to be answered", see below).
- **"This message is ONLY a push notification and NOT appears in the chat"
  is mutually exclusive with the entire cascade/deactivate/recall block.**
  Use "This message is ALWAYS announced by a push notification" instead if
  both push-notification delivery and cascade behavior are needed — that
  one does not disable the cascade checkboxes.
- **"This message expects to be answered by the participant" is *also*
  mutually exclusive with the cascade/deactivate/recall block**, independent
  of the push-notification finding above — checking it disables
  `deactivates and remembers`, both `recalls...` variants, `clears the
  current dialog cascade`, `clears all dialog cascades`, and `will not be
  cleared on clear all`, regardless of the `blocks the micro dialog`
  checkbox's own state. In short: **cascade-clearing is only available on
  plain, non-answer-expecting messages.** For a multi-message reminder flow,
  this means only the *entry* message can carry cascade-clear — treat that
  as sufficient (the cascade is a dialog-level return-stack concept, not
  something that needs repeating on every message in the flow).
- Checking "expects to be answered" auto-defaults **Answer type** to
  "select one" and reveals **Answer options**, **Store message reply to
  variable**, and **Store the following value in case of no reply** — the
  same field group used throughout this coaching's existing Yes/No
  questions (precedent: `$mySpiro_spirometerWithinReach`, options `Yes:1
  No:0` / `Da:1 Nu:0`, no-reply sentinel `-99`).
- The **Answer type** filterselect (`free text`, `free text multiline`, `free
  numbers`, `likert` [3 variants], `select one`) is a *different* dropdown
  from a similarly-generic-looking one reading `plain`/`html`/`llm one
  shot`/`llm session` that appears nearby — don't confuse them; the second
  one is unrelated to answer configuration (never identified what it's for,
  wasn't needed here).
- The `Store message reply to variable` / `no reply` fields are **not**
  bilingual (plain single-value popups) — only message text and answer
  options need the tab-switch treatment.

### Decision points

- **A decision point's outer "Create/Edit micro dialog decision point:" form
  has its own top-level Comment field AND a nested tree of rules** — each
  rule, once you drill into it, is a **much richer form** than a Rules-tab
  rule: Comment / Rule[x] / operator / Term[y] / Store result to variable,
  then **three mutually-exclusive action checkboxes** ("Leave this decision
  point... if TRUE", "Stop this complete micro dialog... if TRUE", "Update
  participant to newer coaching... if TRUE" — checking any one disables the
  other two), "Assigned units to reset if TRUE", and finally **four jump
  fields**: `Cascade to other dialog if TRUE`, `Jump to other dialog if
  TRUE`, `Jump to dialog message if TRUE`, `Jump to dialog message if
  FALSE`.
- **This per-rule editor opens as a genuinely separate stacked `.v-window`**
  (window[1] = "Create/Edit rule:", on top of window[0] = the outer decision
  point), not inline in the same window — despite looking, from the button
  list alone, like it might replace the same window's content. Playwright
  window-count checks right after a click can race (`windows: 1` when it's
  actually about to become 2); **always re-check after a short wait rather
  than trusting one immediate read**, and target `.v-window` **last**
  (topmost) for the nested rule's own fields, never `.v-window` **first**
  (the Rules-tab helpers in `_rules_nav.py` assume `wins[0]` — wrong here,
  needed a `wins[-1]`-targeting variant, see `dp_rule_helpers.py` pattern
  used this session, not yet promoted into a shared module).
- **The outer decision-point form has *three* different "Edit" buttons**,
  and picking the wrong one silently opens something unrelated rather than
  erroring: the 1st is the decision point's own top-level Comment, the 2nd
  opened an unrelated, apparently-unused "Edit update transition point:"
  popup (empty, never identified what it's for), and the **3rd (0-indexed:
  2) is the one that opens the currently-selected tree node's own rule
  editor**. Always target the 3rd, never `.first`.
- **`New` at the decision-point-tree level is unreliable for nesting** —
  exactly the same failure mode already documented for the Rules tab
  (`autochanges/2026-09-11-alex-v02-phase3.2-*`, `phase3.3-*`): selecting a
  node and clicking `New` sometimes correctly nests a child under it,
  sometimes creates a sibling instead, with no visible error either way —
  **always verify the resulting node's tree depth before trusting it.**
  `Duplicate` (select a node, click `Duplicate`) is reliable for creating
  a same-depth **sibling** — used to build the three-way `$dummyVar`
  branch and confirmed correct every time.
- Some checkboxes here needed **`click(force=True)`** — a plain
  `locator.click()` on "Stop this complete micro dialog after this rule if
  rule result is TRUE" silently did nothing (no error, checkbox stayed
  unchecked) three separate times; `force=True` worked immediately every
  time. Not yet root-caused (possibly the checkbox's own bounding box is
  covered by a sibling label element that intercepts the click); worth
  trying `force=True` first if a checkbox click in this form doesn't stick.
- **`Jump to dialog message if TRUE/FALSE`** lists only the *current*
  dialog's own messages (small, single-page list, matched by the message's
  comment shown as a `[Comment text] message preview` string). **`Jump to
  other dialog if TRUE`** lists *every* dialog in the coaching and needs the
  same pagination-search technique as the Rules tab's `Micro dialog to
  start` selector (10 items/page, click `.v-filterselect-nextpage` until
  found — reused the existing `paginate_and_click` helper unchanged).
- **`New Message` / `New Decision Point` always append at the very end** of
  the *current* dialog's row list, regardless of what's selected — same
  behavior as the Rules tab's `New`/`Duplicate` appending at the end of a
  parent's children. Use `Move Up` / `Move Down` to reposition afterward
  (each click moves one position; plan the exact count from the row list,
  and always show sensitivity to be careful with an odd, unexplained
  reordering: two rows I hadn't touched in between (`wait` and the
  freshly-added `completion-check`) swapped order once, between two
  otherwise-unrelated actions — cause not identified, fixed by one more
  `Move Up`. Always re-dump the row list after any add/move rather than
  trusting the last-known order.)
